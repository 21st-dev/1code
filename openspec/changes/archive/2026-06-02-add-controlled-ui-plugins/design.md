## Context

Previous plugin governance changes established:

- Manifest-only plugin discovery for Claude Code and Codex plugin packages.
- Local manifest fingerprints, advisory store/source pins, and review state.
- Plugin safe mode and main-process safety gates.
- Plugin Doctor/Debug facts.
- Runtime component gates for Claude plugin commands, skills, agents, and MCP.

The next useful capability is not a compatibility layer for Codex++ tweaks. It is a Locus-native controlled UI layer that lets a reviewed plugin declare UI contributions while Locus keeps rendering, state, and actions under its own code.

## Goals

- Let reviewed plugins contribute limited UI surfaces through static manifest data.
- Keep all renderer output generated by Locus-owned React components.
- Keep all actions mediated by main-process APIs and allowlists.
- Make contribution eligibility visible in Settings > Plugins and Doctor/Debug.
- Preserve safe mode as a recovery switch for contributed actions.
- Keep controlled UI gates separate from MCP/runtime gates.

## Non-Goals

- No plugin JS execution.
- No DOM patching.
- No raw Markdown/HTML rendering from plugins unless sanitized and separately approved; first slice should prefer plain text and structured components.
- No iframe/webview plugin pages.
- No plugin-authored CSS injection, portals, or click handlers.
- No filesystem, shell, provider-secret, SQLite, native bridge, or arbitrary MCP access from UI contributions.
- No automatic marketplace install/update.

## Contribution Manifest

Decision: Use a Locus-native contribution manifest, separate from Claude/Codex runtime internals.

Suggested first path:

```text
<plugin-root>/.locus-plugin/ui.json
```

The manifest is optional. If absent, the plugin remains `manifest-only`.

The manifest is parsed only in Electron main, with a strict schema and bounded limits. Unknown fields are ignored or surfaced as warnings. Invalid manifests produce diagnostics and no active contributions.

Example shape:

```json
{
  "version": 1,
  "surfaces": [
    {
      "id": "review-settings",
      "type": "settings-section",
      "title": "Review Settings",
      "description": "Static plugin preferences rendered by Locus.",
      "fields": [
        { "id": "severity", "type": "select", "label": "Severity", "options": ["low", "medium", "high"] }
      ]
    },
    {
      "id": "review-panel",
      "type": "workbench-panel",
      "title": "Review",
      "items": [
        { "type": "text", "text": "Prepare a review prompt for this project." }
      ]
    },
    {
      "id": "prepare-review",
      "type": "command-button",
      "label": "Prepare review",
      "action": {
        "type": "insert-chat-draft",
        "prompt": "Review the current diff and list blocking issues first."
      }
    }
  ]
}
```

## Eligibility Gate

Controlled UI contributions are eligible only when:

- The plugin is currently discovered.
- The current contribution manifest is included in the reviewed fingerprint.
- The plugin fingerprint is locally reviewed.
- Safe mode is disabled for action execution.
- The runtime/source is allowed for controlled UI.
- The contribution schema validates.

Decision: Add a dedicated controlled UI gate instead of reusing `canUseMcp`.

Suggested gate fields:

```ts
interface PluginControlledUiGate {
  canRenderControlledUi: boolean
  canInvokeControlledAction: boolean
  blockedReasons: Array<
    | "safe-mode"
    | "review-required"
    | "review-changed"
    | "invalid-contribution-manifest"
    | "unsupported-runtime"
    | "unsupported-surface"
    | "unsupported-action"
    | "permission-not-granted"
  >
}
```

Main process must recompute this gate when listing contributions and again when invoking an action. The renderer must never decide that a contribution is trusted.

Codex plugin cache packages remain read-only by default. If a future Locus-owned Codex plugin execution primitive exists, it needs a separate spec before Codex packages can become active controlled UI providers.

## Rendering Model

Renderer receives normalized contribution data from tRPC. It does not read plugin files and does not evaluate plugin code.

Allowed first-slice components:

- Text blocks.
- Description rows.
- Key/value facts.
- Select, checkbox, text input fields for per-plugin preferences.
- Command buttons backed by allowlisted action types.

Disallowed:

- Raw HTML.
- Remote script/style/image injection.
- JSX/component references.
- Arbitrary markdown extensions.
- User-provided event handlers.
- iframe/webview plugin pages.
- Plugin-authored CSS capable of overlaying or clickjacking app controls.

## Action Model

Command buttons call a main-process `plugins.invokeControlledAction` mutation with:

- `pluginReviewKey`
- `contributionId`
- `actionId`
- user-visible confirmation state if required

Main process must re-resolve the plugin, rescan the current contribution manifest, compare the reviewed fingerprint, recompute safe mode and controlled UI gates, and then execute only allowlisted Locus-owned actions.

Allowed first action:

- `insert-chat-draft`: prepares text in the active chat draft or returns a draft payload for renderer insertion. It does not send a message or execute an agent.

Blocked actions:

- Shell execution.
- File writes.
- MCP approval.
- Plugin enable/disable.
- Provider credential access.
- Direct database access.
- Chat send/agent execution.

## Permission Grants

Decision: Treat controlled UI permissions as fingerprint-bound local grants.

Grant records should include:

- plugin review key
- contribution manifest fingerprint
- surface id
- action id or setting field id
- requested permission id
- granted timestamp

If contribution metadata changes, the current fingerprint changes and previous grants become stale. Stale grants must be visible in Doctor/Debug and must not authorize action invocation.

## State Model

If settings fields are implemented in the first slice, values are stored under app-managed per-plugin state:

```text
plugin-data/<runtime>/<review-key>/controlled-ui-state.json
```

State writes go through main-process schema validation. Plugins never receive raw access to the Locus SQLite database or user data root.

## Doctor / Debug

Doctor should report:

- Number of controlled UI contributions per plugin.
- Invalid contribution manifest diagnostics.
- Whether contributions are blocked by safe mode, review state, read-only Codex cache, or schema validation.
- Whether any command action is disabled because it is not allowlisted.
- Controlled UI gate reasons.
- Stale controlled UI permission grants.

Debug should show bounded identifiers and counts, not raw secrets or plugin source code.

## Risks / Mitigations

- Risk: Users mistake controlled UI for safe arbitrary plugins.
  - Mitigation: UI copy says Locus renders declared surfaces; it is not a sandbox or trust certificate.
- Risk: Plugin-authored text becomes misleading or phishing-like.
  - Mitigation: Keep source/plugin identity visible on every contribution and keep actions user-mediated.
- Risk: Contribution schema grows into a mini programming language.
  - Mitigation: Keep declarative components small and reject loops, expressions, remote code, and arbitrary event handlers.
- Risk: Safe mode appears ineffective if panels still render.
  - Mitigation: Safe mode may show read-only contribution metadata, but disables contributed actions and labels them blocked.
- Risk: Renderer forges a contribution/action payload.
  - Mitigation: Main process ignores renderer-provided trust state and recomputes current plugin, fingerprint, safe mode, gates, and action declaration before invocation.

## Implementation Order

1. Add shared contribution schema, validation, and eligibility types.
2. Add main-process contribution discovery from reviewed plugin roots.
3. Include contribution data in review documents and Doctor/Debug.
4. Expose read-only contribution lists and gated action invocation through the plugins router.
5. Render Settings contribution sections and command buttons.
6. Add a workbench panel host only after Settings rendering is stable.
7. Add tests, source guards, desktop smoke, screenshot, and recording evidence.
